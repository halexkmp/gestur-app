# Tirolesa API

Daily audit of tirolesa descents detected by a device against descents sold.

## Endpoints

POST /tirolesa/trips → 201

POST /tirolesa/devices/heartbeat

POST /tirolesa/devices → 201

GET /tirolesa/devices

PUT /tirolesa/devices/{device_id}

POST /tirolesa/products → 201

GET /tirolesa/products

DELETE /tirolesa/products/{tirolesa_product_id} → 204

GET /tirolesa/audit?date_from={date}&date_to={date}

POST /tirolesa/audit/justifications → 201

DELETE /tirolesa/audit/justifications/{justification_id} → 204

---

## Authentication

Device endpoints use `X-Device-Key: <key>`, returned once by `POST /tirolesa/devices`.
All other endpoints use the bearer token and `Requires: ADMIN or MANAGER`.

---

## Devices

### POST /tirolesa/devices → 201

Requires: ADMIN or MANAGER

Request:

```text
name
```

Response. `api_key` appears only here and cannot be retrieved later:

```text
id
name
active
created_at
api_key
```

### GET /tirolesa/devices

Requires: ADMIN or MANAGER

```text
[
  {
    id
    name
    active
    last_seen_at   # nullable
    offline        # true when active and not seen for 15 minutes
  }
]
```

### PUT /tirolesa/devices/{device_id}

Requires: ADMIN or MANAGER. 404 when the device does not exist.

To replace a key, set `active` to false and create a new device.

Request, all optional:

```text
name
active
```

Response:

```text
id
name
active
last_seen_at   # nullable
```

## Device endpoints

### POST /tirolesa/trips → 201

Requires: `X-Device-Key`

Sent once per trip by the finish side, so a request proves the descent finished.

Request, all required:

```text
id      # UUID generated by the device, identifies the trip
start   # datetime with a timezone offset
end     # datetime with a timezone offset
```

Response:

```text
id
duplicate   # true when this id was already recorded
```

- 201 when the trip is new, 200 when `id` was already recorded. Resending is always safe.
- A datetime without a timezone offset returns 422.
- A trip is kept but marked as clock suspect when `start` or `end` is over 5 minutes in
  the future, `start` is over 7 days old, or `end` is not after `start`.

### POST /tirolesa/devices/heartbeat

Requires: `X-Device-Key`

Sent every 5 minutes. No request body. Use `server_time` to resync the device clock.

```text
server_time
```

## Tirolesa products

Links a product to the audit. Only linked products count as descents sold.

### POST /tirolesa/products → 201

Requires: ADMIN or MANAGER. 404 when the product does not exist, 409 when already linked.

Request:

```text
product_id
units_per_descent   # default 1, minimum 1
```

`units_per_descent` is how many sold units make one descent. Solo and tandem products
sold as one descent use 1. A product sold per person that always rides in pairs uses 2.

Response:

```text
id
product_id
units_per_descent
```

### GET /tirolesa/products

Requires: ADMIN or MANAGER

```text
[
  {
    id
    product_id
    product_name
    units_per_descent
  }
]
```

### DELETE /tirolesa/products/{tirolesa_product_id} → 204

Requires: ADMIN or MANAGER. 404 when the link does not exist.

## Justifications

Explains descents that have no sale, such as test or courtesy rides.

### POST /tirolesa/audit/justifications → 201

Requires: ADMIN or MANAGER

Request:

```text
audit_date   # local date
quantity     # descents, minimum 1
type         # TirolesaJustificationType
reason       # required, not empty
```

Response:

```text
id
audit_date
quantity
type
reason
created_at
```

### DELETE /tirolesa/audit/justifications/{justification_id} → 204

Requires: ADMIN or MANAGER. 404 when missing or already deleted.

The record is kept with who deleted it, and stops counting in the audit.

## Daily audit

### GET /tirolesa/audit?date_from={date}&date_to={date}

Requires: ADMIN or MANAGER

Both params are required local dates, inclusive. 400 when `date_from` is after `date_to`
or the range exceeds 62 days.

Returns one row per date in the range, oldest first, including days with no activity.
Days use the local offset from the lateness configuration, falling back to UTC-3.

```text
[
  {
    date
    descents_detected              # trips on this local date, placed by start
    descents_sold                  # from linked products on non-canceled sales
    descents_below_default_price   # part of descents_sold, sold below default_price
    descents_justified
    unexplained                    # detected - sold - justified, floored at 0
    sold_above_detected            # sold + justified - detected, floored at 0
    sales_amount                   # total_price of linked products' sale items
    estimated_unpaid_value         # unexplained x average price per descent
    status                         # TirolesaAuditStatus
    device_hours                   # hours the device was seen on this local date
    clock_suspect_trips            # clock suspect trips, placed by when they arrived
    sensor_warning                 # device_hours is 0 or clock_suspect_trips > 0
    justifications: [
      {
        id
        quantity
        type        # TirolesaJustificationType
        reason
        created_by: { id, name }
        created_at
      }
    ]
  }
]
```

Status:

- `UNEXPLAINED`: more descents were detected than sold and justified.
- `SOLD_ABOVE_DETECTED`: fewer descents were detected than sold and justified. This
  means a sensor failed or a sale had no ride, so it carries no money value.
- `BALANCED`: the numbers match.

`descents_below_default_price` does not affect `status`, because discounts and partner
prices are normal. A high value is worth a manager's attention, since a R$0 sale could
cover an unsold ride. It compares with the product's current `default_price`.

Figures for past days can change if the device delivers delayed trips later.
